# 0025 — ドメイン無し構成の L2 は DNS を 1 つも持たない（名前解決が全滅する）

## 症状

ドメインを作らない L2 宣言（`domain:` を書かない構成）で bootstrap すると、Windows L2 の
`configure_windows_baseline.yml` が最初のタスクで落ちる。

```
TASK [windows_baseline : Prepare WinGet for the current remote user]
fatal: [arcwin01]: FAILED! => ...
  "message": "プロバイダー 'NuGet' について、指定された検索条件に一致するものが見つかりませんでした。"
  "host_out": "WARNING: 利用可能なプロバイダーの一覧をダウンロードできません。インターネット接続を確認してください。"
```

「インターネット接続を確認してください」と出るが、**L2 からインターネットへは出られている**
（ルーテッド LabNAT + 二段 NAT は正常。IP 指定なら通る）。落ちているのは**名前解決だけ**。

同じ宣言でも `domain:` があると再現しない。そのため「AD 構成では動くのに、単体 VM だと動かない」
という紛らわしい出方になる。

## 原因

resolver が **DNS をドメインがある時しか設定していなかった**。

```python
# 修正前
dns = dns_default if spec.get("domain_join") else None   # domain が無ければ None
nic = {"switch": switch, "ip": ip, "gw": gw}
if dns:
    nic["dns"] = dns                                      # ← 付かない
```

そして受け取る側 `Initialize-L2Access.ps1` が、DNS 未指定のときに**ゲートウェイへフォールバック**
していた。

```powershell
# 修正前
Dns = if ($vm.nics[0].dns) { $vm.nics[0].dns } else { $vm.nics[0].gw }
```

ゲートウェイ (10.10.0.1) は **L1 = ルーター兼 NAT であって DNS サーバーではない**。DNS を
そこへ向けると、クエリは投げられるが誰も応答しないので**全滅する**。ルーターは DNS も
やってくれる、という家庭用ルーターの感覚がそのまま持ち込まれていた。

Linux 側は `New-CloudInitSeed.ps1` が既定 `1.1.1.1 / 8.8.8.8` を持っていたため**動いてしまい**、
「Linux は繋がるのに Windows だけ落ちる」という非対称も生んでいた。

## 対策

**DNS を宣言できるようにし、解決順を明示する。** `dns` を継承可能フィールドに追加した
（`defaults` / `group` / VM / `overrides` のどこでも書ける）。

```yaml
defaults:
  dns: 10.10.0.99          # 単一でもリストでも書ける
groups:
  - name: web
    dns: [10.10.0.98, 1.1.1.1]
```

resolver の解決順（`resolve_dns()`）:

1. 宣言の `dns`
2. ドメイン参加なら最初の DC の IP（従来の自動補完）
3. 既定の公開リゾルバ `1.1.1.1 / 8.8.8.8`（Linux の cloud-init シードと同じ既定）

戻り値は**常にリスト**へ正規化する。`Set-DnsClientServerAddress` も netplan の
`nameservers.addresses` もリストを受けるため、消費側の分岐が消える。
`Initialize-L2Access.ps1` のゲートウェイへのフォールバックは**削除**した（DNS でないものを
DNS として設定するのは、無設定より悪い。無設定なら「DNS が無い」と気づけるが、
ゲートウェイが入っていると設定済みに見える）。

## 教訓 / 汎用ノウハウ

- **フォールバック先は「それらしい値」ではなく「正しい値」でなければならない。** ゲートウェイを
  DNS の既定にするのは、動かないうえに**設定済みに見える**ぶん無設定より有害。妥当な既定が
  無いなら、フォールバックせず fail-fast させるほうがよい。
- **オプション機能を外した構成こそ壊れている。** ここでは AD が「常に居るもの」として暗黙の前提に
  なっており、DNS の供給元が AD に依存していた。**最小構成（何も足さない宣言）を定期的に
  流さないと、この種の依存は見つからない。**
- **同じ設定項目の既定値が実装経路ごとに違うと、症状が非対称になって診断が遅れる。**
  ここでは Linux (cloud-init: 公開リゾルバ) と Windows (PS Direct: ゲートウェイ) で既定が
  食い違っていた。既定値は**モデル側 (resolver) に 1 つだけ**置き、各経路はそれを配るだけにする。
- 「インターネット接続を確認してください」という**エラーメッセージを額面どおり受け取らない**。
  疎通 (IP) と名前解決 (DNS) は別物で、後者だけ壊れているケースが非常に多い。
